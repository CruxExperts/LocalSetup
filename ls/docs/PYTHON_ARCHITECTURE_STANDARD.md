# Python Architecture Standard

Purpose: define the preferred Python environment and package design pattern for LocalSetup framework tooling and LocalSetup-generated Python project guidance.

# Scope And Authority

This standard has three authority levels:

- **LocalSetup framework code:** mandatory for new Python modules and substantially refactored Python tooling. Existing oversized or mixed-responsibility files are baseline-managed until intentionally rebuilt.
- **New LocalSetup-generated Python projects:** default recommendation for environment and package layout guidance.
- **Existing downstream projects:** advisory only. LocalSetup must not rewrite or take ownership of downstream `.venv`, `pyproject.toml`, `.python-version`, lockfiles, or packaging layout without explicit user approval.

This document separates upstream-supported rationale from LocalSetup policy. Upstream packaging and runtime docs describe generally supported Python behavior. LocalSetup policy chooses a stricter operating shape so agents can make small, testable changes without expanding old script debt.

# Environment Standard

LocalSetup framework tooling targets Python >= 3.12 and runs from the repo-managed uv environment unless a documented wrapper delegates elsewhere.

For LocalSetup framework code:

- Keep dependency state in `pyproject.toml` and `uv.lock`.
- Use isolated project environments; do not mutate system Python for framework development.
- Treat virtual environments as disposable runtime state, not source-controlled application code.
- Do not repair, delete, or replace a downstream project's own `.venv` unless the user explicitly asks for that downstream environment to be managed.

For LocalSetup-generated Python project guidance:

- Prefer `pyproject.toml` for project metadata and tool configuration.
- Prefer a project-local virtual environment that can be deleted and recreated.
- Prefer `uv` for package, environment, tool, and script workflows unless the target repository declares another manager.

# Package Layout

New importable LocalSetup framework logic should live under `ls/core/<domain>/` as a package. Public direct-execution scripts under `ls/tools/` should be thin wrappers that resolve the repo root, import the package CLI, and return its exit code.

Preferred shape:

```text
ls/tools/<tool_name>.py
ls/core/<domain>/
  __init__.py
  cli.py
  config.py
  models.py
  rules.py
  reporting.py
```

Use the modules that fit the actual tool; do not create empty abstractions. For published Python packages generated by LocalSetup, prefer the standard `src/<package>/` layout when the project is intended to be installed or distributed. For repo-local LocalSetup framework code, `ls/core/` is the established source package root.

# Module Responsibilities

- `cli.py`: argument parsing, command dispatch, and output mode selection only.
- `config.py`: load and validate user-provided files, environment-derived settings, and baselines.
- `models.py`: dataclasses, typed payloads, and stable finding/result shapes.
- `rules.py`: deterministic policy evaluation without filesystem traversal side effects.
- `scanner.py` or `inventory.py`: tracked file discovery and content measurement.
- `reporting.py`: JSON, markdown, and terminal rendering.
- Thin wrappers in `ls/tools/`: no policy logic beyond import path setup and `main()` delegation.
- `__init__.py`: package metadata and lightweight exports only; no CLI imports or expensive runtime work.

Package-local `utils.py` is allowed only when it has a narrow package-local purpose. Prefer named modules that describe responsibility.

# File Size Rules

Line count uses actual UTF-8 file content with replacement for invalid bytes and `splitlines()`. It is not AST logical line count.

- 500 lines: warning threshold. Review responsibility boundaries before adding more logic.
- 700 lines: baseline required for adding logic.
- 1000 lines: baseline required for compatibility-only or refactor-only work.

Baseline rules:

- No glob exemptions.
- Paths are repo-relative POSIX paths.
- Deleted paths produce stale-baseline warnings.
- Renamed files are new files unless the baseline is intentionally updated in the same reviewed change.
- A baseline entry must include a non-empty reason and owner.

# Tooling And Validation

Use the architecture checker when changing Python framework tooling:

```bash
uv run --locked python ls/tools/python_architecture_check.py \
  --repo-root . \
  --baseline ls/config/python-architecture-baseline.json
```

Ruff is the preferred configured lint, format, and import-sort tool when a project declares Ruff. Ruff is not a hard installed requirement for every downstream project and must not be added to a project solely because LocalSetup is present.

For projects that declare Ruff, run import sorting, formatting, then lint:

```bash
ruff check --select I --fix
ruff format
ruff check
```

Type checkers such as mypy or Pyright are recommended when the project already enables them. LocalSetup does not add them in this standard by itself.

# Refactoring Rules

When refactoring existing framework debt:

- Preserve public command contracts, JSON payload keys, exit codes, documented paths, and delegated `localsetup` behavior.
- Inventory compatibility before moving implementation out of an oversized wrapper.
- Move logic into domain packages in small, testable pieces.
- Keep wrappers stable and direct-executable.
- Update the baseline only when debt improves, intentionally moves, or needs a reviewed temporary exception.
- Do not use a large line-count reduction as the success metric; behavior preservation and clearer responsibility boundaries are the success criteria.

# Source Evidence

Access date for source checks: 2026-06-05.

- Python `venv` official docs: https://docs.python.org/3/library/venv.html. Upstream support: virtual environments are created with `python -m venv`; environments are disposable, not source-controlled, and should be recreated rather than moved. LocalSetup policy uses this to keep framework and downstream environment ownership separate.
- Python Packaging User Guide, Installing packages using pip and virtual environments: https://packaging.python.org/en/latest/guides/installing-using-pip-and-virtual-environments/. Upstream support: project-local virtual environments isolate package installation and should be excluded from version control. LocalSetup policy uses uv by default, but the environment ownership principle is the same.
- Python Packaging User Guide, Writing your `pyproject.toml`: https://packaging.python.org/en/latest/guides/writing-pyproject-toml/. Upstream support: `pyproject.toml` is used by packaging and other tools, with `[build-system]`, `[project]`, and `[tool.*]` tables. LocalSetup policy recommends it for generated Python project metadata.
- Python Packaging User Guide, `src` layout vs flat layout: https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/. Upstream support: `src` layout separates import packages from repository root files and requires installation to run importable code. LocalSetup policy recommends this for generated distributable Python packages while retaining `ls/core/` for framework code.
- Python Packaging User Guide, Packaging Python Projects: https://packaging.python.org/en/latest/tutorials/packaging-projects/. Upstream support: examples use `pyproject.toml`, `src/<package>/`, `__init__.py`, and `tests/`. LocalSetup policy uses this as generated-project guidance, not as a mandate for existing downstream repositories.
- Ruff linter docs: https://docs.astral.sh/ruff/linter/. Upstream support: `ruff check` runs lint checks and `ruff check --fix` applies safe fixes by default. LocalSetup policy uses `ruff check --select I --fix` as the configured import-sort step when Ruff is declared.
- Ruff formatter docs: https://docs.astral.sh/ruff/formatter/. Upstream support: `ruff format` is the formatter command, the formatter does not currently sort imports, and it is designed to run alongside Ruff's linter. LocalSetup policy orders import sorting, formatting, then lint for projects that declare Ruff.
